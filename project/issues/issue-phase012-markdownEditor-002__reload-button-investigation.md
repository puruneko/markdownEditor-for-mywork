# リロードボタンが機能しない不具合の再現確認と原因の切り分け（調査 issue・修正は別 issue）

## 1. Background（背景）

`修正したい箇所.md` の common 節:

> →追加要望。上部のリロードボタンが機能していない。強制で再mdパース依頼と最新md情報の反映と再描画を行うようにして。フィルタなどの設定はクリアしないようにして。

**この issue はリロード機能を修正するものではない。原因を再現・特定し、その結果を記録することが目的である。** 修正は、本 issue の結果を受けて別途起票される（`issue-phase012-markdownEditor-003` 以降の番号、または新規 issue）。

### 現在の実装（コード上、確認済みの事実）

- リロードボタン（⟳）は `src/lib/query/FilterBar.svelte` にあり、`onReload` プロパティが渡されている場合のみ描画される。`FilterBar` は Calendar / Gantt / Kanban / Ast の各ビューのマウントコンポーネントで使用されている。**Dashboard のマウントコンポーネント（`DashboardViewMount.svelte`）には `FilterBar` の呼び出しが存在せず、ボタン自体がない。**
- `onReload` の実体は `src/views/ShadowItemView.ts` にある:
  ```ts
  const onReload = (): void => {
    if (this.astIndex) {
      void this.astIndex.forceReparse()
    } else {
      void this.fileSync.forceReparse()
    }
  }
  ```
- `AstIndex.forceReparse()`（`src/sync/ast-index.ts`）は `initialScan()` を呼び直す。`initialScan()` はスコープ内（vault / folder / current-file）の Markdown ファイルを列挙し、ファイルごとに `updateFile(file)` を呼ぶ。`updateFile` は `app.vault.read(file)` で**ディスク上の内容**を読み直し、`parseMarkdown` でパースし直し、`this.notify()` を呼ぶ（ファイルごとに毎回 `notify()` が呼ばれる。1回のリロードでバッチ化されていない）。
- `notify()` は登録済みの `updater` コールバック（Svelte 側の `sources` state を更新する関数）を呼ぶ。フィルタの状態（各 `*ViewMount.svelte` の `query` という別の state 変数）は `onReload` の処理経路に一切含まれておらず、リロードを実行してもクリアされない構造になっている（コード上、この点についての明確な不具合は見当たらない）。
- `forceReparse` / `onReload` を対象にした自動テストはリポジトリ内に存在しない。

### 判定すべき仮説

コードを静的に読む限り、ボタンのクリックからディスク再読み込み・再パース・購読者への通知・Svelte state の更新までの一連の呼び出しチェーンに、明確な欠落は見当たらない。そのため、「機能していない」という報告の原因は、次のいずれか、または複数の組み合わせであると考えられるが、**実機での再現確認なしには判別できない**。

- H1: `forceReparse` は Obsidian の `vault.read()`（ディスク上の内容）を読み直すため、**エディタで編集した直後、まだファイルに保存されていない変更は反映されない**。ユーザーが編集直後にリロードを押した場合、変更前の内容のまま再表示され、「機能していない」ように見える可能性がある。
- H2: リロードを押しても、内容に変化がなければ画面の見た目は変わらず、かつボタンを押したことへの視覚的なフィードバック（処理中の表示、完了通知など）が一切ないため、ユーザーが「動いていない」と感じている可能性がある。
- H3: いずれかのライブラリ（calendar / gantt / kanban）の Svelte コンポーネントが、`sources` prop の更新以外に内部状態（ローカルの store やキャッシュ）を持っており、`sources` が更新されてもその内部状態が古いままで、結果的に画面に反映されない可能性がある。
- H4: ユーザーが実際に操作しているのが Dashboard タブであり、そもそもボタンが存在しない（実装漏れ）ことを「機能していない」と表現している可能性がある。

## 2. Objective（目的）

上記 H1〜H4 のうち、実際に発生している原因（複数該当する場合はすべて）を実機での再現確認によって特定し、記録する。あわせて、再現確認に使った手順を自動テスト（可能な範囲）として残す。

## 3. Scope（スコープ）

- エディタでの未保存の編集がある状態でのリロードの挙動確認。

## 4. Implementation requirements（実装要件）

### ステップ1: 自動テストによる再現確認（`npm run test:obs:e2e` が実行可能な場合）

3. 書き換え後の内容が画面に反映されることを確認する（H3 の判定: 反映されなければ、該当ライブラリの内部状態にキャッシュがある可能性が高い）。

5. 別のシナリオとして、エディタで対象ファイルを開いて内容を編集し、**保存する前に**リロードボタンを押し、表示内容がどうなるかを記録する（H1 の判定）。
