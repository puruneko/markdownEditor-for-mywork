1. エグゼクティブサマリー — 完成度の結論

本プロダクトは「素の Markdown を唯一の正とし、AST を介して 7 つのビュー（AST / Calendar / Gantt / Kanban / Agenda / Health / Unscheduled Tray）へ双方向同期する」Obsidian プラグインである。前回レポート（6/28）時点で MUST とされた 複数ファイル横断集約・クエリ／フィルタ・繰り返しタスク・Agenda ビュー はすべて実装済みとなり、土台としての完成度は大きく前進した。

85%
基盤（記法・パーサー・双方向同期）
75%
「見る」機能（ビュー・集約・検索）
50%
「書く・操作する」機能（入力体験）
20%
「報告する・振り返る」機能

結論：「情報の散在」「一覧と経緯の分離」「Excel 管理の限界」という悩みは設計レベルで解決済み。「期限と予定の管理」「ステータス把握」は7割方カバーしているが仕上げが残る。一方、「進捗をさっと報告できない」に対応する機能はほぼ未着手であり、上司への報告という当初の動機に照らすと、ここが現時点の最大のギャップである。またステータス把握については、競合（org-mode、Obsidian Tasks）が持つ「完了日・状態変更のタイムスタンプ記録」が欠けており、これが無いと報告機能も作れないため、次フェーズの最優先候補と評価する。

チームへの要点：土台は完成に近い。次に作るべきは「記録の自動化（いつ何をしたかを Markdown に残す）」→「そこからの報告生成」という縦のライン。これは競合にも無い差別化になり得る（§7.1〜7.2）。

2. 評価軸：オーナーの「困りごと」7項目

本レポートは機能の網羅性ではなく、プロダクトオーナー自身が解決したかった悩みを評価軸とする。悩みは以下の 7 項目に整理した。

#困りごと求められる能力
P1情報がいろんなところに散らばるメモ・タスク・予定を 1 つの Markdown に集約し、複数ファイルでも横断して見られること
P2いつまでに終わらせるか／いつやるかが分からず、上司に怒られる期限（@due）と実施予定（@schedule）を別概念として管理し、抜けを検知できること
P3細かいタスクのスイッチが多く、何をどこまでやったか分からなくなるステータスの一目把握と、「中断時点の状態」を記録・復元できること
P4タスク一覧と経緯・詳細がばらばらで確認に時間がかかるタスクの直下にメモ・経緯を持ち、一覧からワンクリックで詳細へ飛べること
P5進捗をさっと報告できない・把握できない「今週やったこと／進行中／遅延」を集計し、報告に使える形で出力できること
P6管理自体の作業が多くて続かない（手動の書き換え・色付け・罫線）記法の入力補助・ドラッグ操作・自動lint など、管理コストを最小化すること
P7Excel は自由に文字を書けず、予定とメモを両立できない自由記述（Markdown）と構造化データ（日付・ステータス）の両立

3. 困りごと別スコアカード（現状実装の評価）

P1 情報の散在 — 集約解決済み 90%

できている：タスク・予定・メモが 1 つの Markdown で共存（demo が実証）。phase001 で 複数ファイル横断の AST インデックス（現在ファイル／フォルダ／Vault スコープ切替、ホットリロード）と クエリ言語＋FilterBar＋埋め込みクエリブロック が実装済み。ファイル横断の identity（globalKey）も確立。

残り：「思いついた瞬間に放り込む」入口が無い。散在の根本原因は記入先を探す手間なので、クイックキャプチャ→インボックス→仕分け（issue-phase003-006、open）が最後のピース。

P2 期限と実施予定の管理概ね対応 70%

できている：@due（期限）と @schedule（開始〜終了の実施予定）を別メタとして一級で扱う設計は、まさに「いつまで」と「いつやるか」の分離。競合の多くは due しか持たない（§5）。Agenda ビューが期限超過／今日／今週を束ね、Health パネルが undated（日付なし）・overdue（期限超過）・stale（放置） を検知する。これは「怒られる前に気づく」仕組みとして直接効く。

残り：①期限が来ても通知が出ない（issue-phase002-005、open）。②未予定タスクをカレンダーへドラッグして予定化する動線（Unscheduled Tray はビュー実装済みだが issue-phase003-001 は open、ドラッグ割付の仕上げ待ち）。③会議など外部カレンダーの予定が見えないため、「空いている時間にタスクを置く」計画が立てにくい（§7.4）。

P3 タスクスイッチとステータス把握部分対応 55%

できている：5 ステータス（todo/doing/blocked/hold/done）は「進行中」「待ち」を区別でき、demo のように [>]＋直下メモで「どこまでやったか」を書ける。Kanban・Agenda・Health でステータスの俯瞰も可能。

欠けている：「どこまでやったか」の記録が全部手書きである点。org-mode はステータス変更時に自動でタイムスタンプとメモ（LOGBOOK）を残し、Obsidian Tasks は完了時に完了日 ✅ 2026-07-03 を自記入する。本アプリはチェックを付けてもいつ完了したかが残らないため、後から「今週何をしたか」を復元できない。スイッチが多い働き方では、この自動記録の有無が体験を分ける（§7.1）。

P4 一覧と経緯の分離解決済み 85%

できている：タスク直下に引用（QuoteNode）・メモを構造として保持し、「〜。信用しきれない。」のような経緯・感情まで書ける（Excel では不可能な芸当）。全ビューからクリックでエディタの該当行へジャンプでき、「一覧で見る→詳細を確認」の往復が数秒で済む。これは競合比較でも独自の強み。

残り：逆方向（エディタ→ビュー）のハイライト（issue-phase003-009、open）と、Kanban カード上でのメモ量プレビューなど微調整。

P5 進捗報告・進捗把握最大のギャップ 20%

できている：Agenda／Health／クエリで「今の状態」は把握できる。グループ進捗ロールアップ（3/5 完了・60%）は issue-phase003-002 で計画済み（open）。

欠けている：「先週何を終えた／今週何をやる／何が遅れている」を報告できる形に集計・出力する機能がゼロ。上司への報告が当初の動機である以上、ここは意図的に投資すべき領域。前提として P3 の完了日記録が必要（記録が無いものは集計できない）。世間では Geekbot や Range のような「タスクデータから status report を自動生成する」ツールが独立ジャンルとして成立しており、需要の強さの証左（§7.2）。

P6 管理コストの最小化（続けられるか）部分対応 50%

できている：ドラッグ→Markdown 書き戻し（色付け・罫線引きが一切不要）、記法 lint＋クイックフィックス、エディタ内ハイライト。「見た目の管理作業」はゼロに近い。

欠けている：入力側の補助がまだ手打ち。日付・メタキーの補完（issue-phase003-008）、クイック追加モーダル（003-004）、チェックボックスのクリックサイクル（003-007）、選択→ビューへドラッグでメタ付与（002-004）がいずれも open。「使わなくなる」リスクは入力の摩擦から始まるため、phase003 の入力系 Issue 群は完成度観点で重要。

P7 自由記述と構造化の両立（脱 Excel）解決済み 95%

できている：Markdown の自由記述の中に @schedule／@due／ステータス記法を埋め込み、そこからカレンダー・ガント・カンバンを「導出」する設計そのものが解。Excel の「予定とメモを両立できない」問題は構造的に発生しない。Git 差分も取れ、可搬性・耐ロックイン性も高い。

5.2 各ツールから採用すべきもの

Obsidian TasksObsidian で最も使われるタスクプラグイン・インライン記法の事実上の標準

強みは「Vault 横断クエリ」と「タスクのライフサイクル日付」。完了時に ✅ 2026-07-03、作成日 ➕、開始可能日 🛫 をタスク行へ自動記録し、done 日でのクエリ（「今週完了したもの」）を可能にしている。繰り返しタスクは完了と同時に次回インスタンスを本文へ生成する方式。

採用候補：① 完了日の自動記録（本アプリなら @done: 2026-07-03 メタが記法体系に自然に収まる）。② 「done 日クエリ」をクエリ言語に追加。③ ステータス変更日 @updated は stale 検知（Health）の精度向上にも直結する。
Emacs org-modeプレーンテキストタスク管理の 40 年級の到達点

本アプリの Agenda はすでに org-agenda に相当。org が今なお上を行くのは ①clocking（タスクへの clock-in/out で実働時間をテキストに記録）、②LOGBOOK（状態変更のたびにタイムスタンプ＋理由を自動追記。WAITING にした瞬間「誰待ちか」を促す）、③custom agenda（保存済みクエリをダッシュボード化）。P3（スイッチで状態を見失う）と P5（報告）への org の回答がまさに ①② である。

採用候補：① [>]（doing）へ切替時に現在時刻を自動追記し、離脱時（別タスクを doing にした時）に自動でメモ行を促す「軽量 clocking」。② blocked へ変更時に「何待ちか」の 1 行入力を促す（demo の運用を機能化）。③ 保存スマートリスト（issue-phase002-007）は org custom agenda の方向で。
NotePlanMarkdown＋カレンダーの商用最有力（Mac/iOS）・時間ブロッキングの代表

「自動生成されるデイリーノート」を軸に、その日のタスク・会議メモ・時間ブロックを 1 ページで扱う。タスクを右側のタイムラインへドラッグして時間ブロック化する UX と、OS カレンダー統合（会議とタスクを同じタイムラインで見る）が高評価の源泉。本アプリのドラッグ書き戻し基盤はこれと同等以上の素質があるが、「会議」が見えない点で日次計画ツールとしては NotePlan に劣る。

採用候補：① 外部カレンダー（ics 購読）の読み取り専用レイヤーをカレンダー／ガントに重ねる。② Unscheduled Tray→カレンダーへのドラッグ割付（issue-phase003-001）は NotePlan の時間ブロッキング UX をベンチマークに。
Todoist非 Markdown 系の王者・入力体験の最高峰

思想は真逆（クラウド DB・サブスク依存）だが、「あす10時 見積送付 #総務 p1」と打つだけで全メタが付く自然言語クイック追加と、確実なリマインド通知は入力・想起コストの基準値。P6（続けられるか）を左右するのはこのレベルの摩擦の低さ。

採用候補：クイック追加モーダル（issue-phase003-004）に日本語日付の自然言語解釈（「明日10時」「来週金曜」）を載せる。通知（issue-phase002-005）は Obsidian Notice＋OS Notification で十分実用になる。
Logseq / TaskForge ほかアウトライナー系・新興 Markdown タスク専業

Logseq はブロック単位のアウトライン＋ジャーナル（デイリーノート）でタスクと経緯を同居させる思想が近い。2026 年時点でも「Markdown タスク管理はソロのナレッジワーカーに最適、チーム共有には不向き」というのが市場の一般的評価であり、本アプリの「個人の業務管理に全振り」という割り切りは市場評価とも整合している。

採用候補：デイリーノート連携（「今日のページ」に today クエリブロックを自動挿入するテンプレート）。新規機能というよりテンプレート＋既存クエリブロックの組み合わせで実現可能。

6. 第三者比較②：コミュニティの Markdown タスク管理実践

ブログ・Reddit・Obsidian フォーラム等で公開されている個人のプレーンテキストタスク管理には、ツール機能ではなく運用パターンとしての知見が蓄積している。本アプリの設計に取り込めるものを 3 つ挙げる。

6.1 Interstitial Journaling（合間ジャーナル）— P3 への直接回答

タスクを切り替えるたびに「時刻＋いまの状態＋次にやること」を 1〜2 行書き残す手法（Tony Stubblebine 提唱、Ness Labs 等で普及）。「タスクの最終状態がログに残るので、戻ったときに即再開できる」効果が知られており、タスク切替時の attention residue（注意の残滓）を減らす研究的裏付けも紹介されている。まさに P3（スイッチで見失う）への世間の回答。

本アプリへの示唆

demo の「電話で催促済み（6/19）」のような経緯メモは、すでに interstitial journaling を手動でやっている状態。これを機能で支援できる。

ステータス変更（特に doing→他）をトリガーに、タスク直下へ - 2026-07-03 14:20 —（カーソル） のタイムスタンプ付きメモ行を自動挿入するオプション。書くか書かないかは自由、行の用意だけ自動化する。

6.2 Bullet Journal 的「デイリーログ＋移送（migration）」— P1/P2 への回答

コミュニティで安定して支持されるのは「まず今日のページに書き殴る→あとで然るべき場所へ移す」二段構え。Obsidian 界隈のワークフロー記事でもデイリーノート起点が主流。「書く場所を考えない入口」があるから散在しない、という逆説が実践知。

本アプリへの示唆

issue-phase003-006（クイックキャプチャ・インボックス・リファイル）はこの実践の機能化であり、方向性は正しい。優先度を上げる価値がある。

キャプチャ先を固定の inbox.md にし、Agenda/Health に「Inbox 未仕分け n 件」バッジを出して移送を習慣化させる（issue-phase002-007 のバッジ機構と統合）。

6.3 「週次レビューを書ける形で残す」— P5 への回答

プレーンテキスト派の報告術は「完了タスクに日付が残っているから、週末に done を日付でフィルタして貼り付けるだけ」という運用が定番（Obsidian Tasks の done クエリ、org-mode の clock report）。ツール側に必要なのは集計より先に「日付の記録」という点で各実践が一致している。ClickUp や Geekbot 等の商用ツールが「タスクデータからの status report 自動生成」を看板機能にしていることも、この需要の強さを示す。

7. 不足機能の提案（優先度・既存 Issue 対応つき）

評価を踏まえた提案。既存Issue は open Issue の優先度付けの参考、新規候補 はガバナンスに従い Issue 化してから着手すること。

7.1 タスクライフサイクルの自動記録 新規候補 — 最優先

なぜ最優先か：P3（どこまでやったか）と P5（報告）の両方の前提。競合（Tasks の ✅、org の LOGBOOK）は標準装備で、本アプリだけが「チェックしたら過去が消える」状態。後から遡って付けられないデータなので、早く入れるほど資産が貯まる。

実装方針：① メタに @done: YYYY-MM-DD（完了日）を追加し、ビュー／エディタ経由の完了操作時に既存の upsert-meta 基盤で自動書き込み。② オプションで doing/blocked への遷移時にタイムスタンプ付きメモ行を自動挿入（§6.1）。③ クエリ言語に done:>=2026-06-30 を追加。手書き完了（エディタで直接 x にする）を検知する場合は差分ベースの補完が必要な点は設計論点。

7.2 進捗レポート生成（週報・日報ドラフト） 新規候補

なぜ：P5 の直接解であり、当初動機（上司への報告）の回収。7.1 のデータが揃えば「先週完了／進行中＋現況メモ／期限超過・リスク」を集計するだけで作れる。タスクの直下に経緯メモを持つ本アプリの構造は、報告文生成において競合より有利（Tasks や Todoist は経緯を持たない）。

実装方針：コマンド「進捗レポート生成」→ 期間（今週／先週／任意）とスコープを指定 → done ／doing＋最新メモ／overdue をセクション別に Markdown で新規ノートへ出力。まずは静的生成で十分。既存の query＋viewmodel を再利用でき、新規はテンプレート整形のみ。

7.3 リマインド通知 issue-phase002-005（open）

なぜ：P2 の残り。「気づく」を Agenda/Health（受動）から通知（能動）へ。前回レポートから継続の宿題であり、競合ではタスク管理の当然の底線。

既存 Issue の方針どおり（常駐タイマー＋Obsidian Notice／OS Notification、リードタイム設定）。7.4 より先に安価に効く。

7.4 外部カレンダー読み取り（ics 購読） 新規候補

なぜ：会議が見えないと「空き時間にタスクを置く」計画が組めず、時間ブロッキング（Unscheduled Tray→ドラッグ割付）の価値が半減する。NotePlan の高評価はカレンダー統合による部分が大きい。

読み取り専用レイヤーに限定（書き戻しの競合問題を回避）。ics URL を設定に登録→カレンダー／ガントに別色で重畳表示。Markdown へは書き込まない。

7.5 入力摩擦の解消（phase003 の完遂） issue-phase003-004 / 006 / 007 / 008、issue-phase002-004

なぜ：P6（続けられるか）の核心。「見る」機能が揃った今、離脱リスクは入力の手間に集中する。クイック追加（自然言語日付つき）・メタ補完／日付ピッカー・チェックボックスサイクル・キャプチャ→インボックスの 4 点セットで、Todoist 級の入力体験に近づく。

既存 open Issue の消化。優先順は 003-008（補完：毎回使う）→ 003-007（クリック操作）→ 003-004／006（追加動線）を提案。

7.6 その他（前回から継続の open 項目）

  • 保存スマートリスト＋バッジ（002-007）— 7.2 のレポートスコープ定義と設計を揃えると二度手間がない。
  • グループ進捗ロールアップ（003-002）— 報告時の「案件単位の進捗率」に直結。7.2 と同フェーズが効率的。
  • 依存矢印と安定 ID（003-003）— 価値はあるが個人業務管理では優先度中。安定 ID は 7.1 の履歴機能とも関わるため設計だけ先行を推奨。
  • 編集可能テーブルビュー（003-005）— Excel からの移行者向け。P7 は解決済みのため優先度は低め。

8. ロードマップ提案（phase004 以降）

現在 phase001–002 完了（横断集約・クエリ・繰り返し・Agenda・Health） 進行中 phase003 入力体験・Kanban 強化（12 Issue 中 1 実装済み） └ 推奨：003-008 → 003-007 → 003-004/006 の順で「入力摩擦」から潰す phase004 記録と報告（本レポートの中核提案） ├ 7.1 @done・状態変更タイムスタンプの自動記録 ← 早いほどデータが貯まる ├ 7.2 進捗レポート生成（週報ドラフト） └ 7.3 リマインド通知（002-005 消化） phase005 計画の完成（時間ブロッキング） ├ 003-001 Unscheduled Tray → カレンダードラッグ割付の仕上げ ├ 7.4 外部カレンダー ics 読み取りレイヤー └ 003-002 進捗ロールアップ／002-007 スマートリスト

判断基準の提案：「その機能が無いと、6 つの悩みのどれかが再発するか？」で優先度を測る。この基準では、phase004（記録と報告）は P3・P5 の再発防止に直結する一方、テーブルビューや依存矢印は再発を招かないため後回しにできる。
