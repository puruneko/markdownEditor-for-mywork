1. 確定の核心 — 時間メタ 3 層モデル

Q2 の回答により、時間に関するメタは「拘束の強さが異なる 3 層」＋横断修飾子「仮置き ?」として体系化された。これが本アプリの時間表現の基本モデルとなる。

メタ意味（宣言）値の形式主な表示先
@plan 「この期間の中でタスクを実施しなければならない」。バッファを含めた予定枠（WBS のイメージ） 期間。日時精度は任意。日付のみの場合は終日（00:00〜23:59）と解釈 Gantt（点線枠）。Calendar はデータを受け取るが表示しない（将来検討）
@schedule 「ここでタスクをやる」。予定というより「この時間に私はこの作業をする」という意思表示（時間ブロック） 期間（開始/終了）。既存仕様どおり Gantt（バー）・Calendar（イベント）
@due 「ここまでにタスクを終わらせる」。期限・締め切り・デッドライン 基本は日付一点。期間指定も可（例：受入期間の締め） Gantt（マイルストン◆。期間なら両端◆＋間を塗り）・Calendar（太い横線＋左端矢印で「ここまで」感）
? 修飾子 仮置き。上記 3 メタすべてに適用可（@plan?: @schedule?: @due?:） キー末尾に ? 全ビューで「仮」であることを文字・見た目で明示（半透明＋?バッジ等）
制約（確定）
  • タスクは @plan / @schedule / @due のいずれか 1 つ以上が必須（どれも無い＝Health の undated 対象）。
  • 時間軸上の整合：plan.start ≤ schedule ≤ plan.end ≤ due(end)。違反しても入力は禁止しないが、バリデーション結果はエラーとして提示する。
  • グループ（親タスク）にも 3 メタすべて付与可（Q3）。
  • @plan が無いタスクは、祖先に @plan があれば内部的に引き継ぐ。Markdown への自動追記は行わず、バリデーション等の内部利用に限る（Q2）。
3 層の関係（1 タスクの時間表現） |-------------------- @plan（この間でやる・WBS 枠）--------------------| | ■■■■ @schedule（ここでやる・意思表示）■■■■ | |----------------------------------------------------------------------| ◆ @due（ここまでに終わらせる） バリデーション：plan.start ≤ schedule ≤ plan.end ≤ due(end)　※違反＝エラー表示（入力自体は許可）
命名の保留：「schedule」という名前は意味（意思表示・時間ブロック）に対して適切か、オーナー自身が再考中。参考案：@do（やる宣言・最短）／@work／@slot（時間ブロック感）／@focus。Q1 の決定（ファイルは正規形・入力は補完で短縮）により、改名してもファイル互換の一括変換は lint クイックフィックスで可能なため、Spec 起票時までに決めれば十分。ただし決めた後の再改名はコストが高いので、Spec 化の時点で確定させること。

2. 各ビューの描画仕様（確定）

2.1 Gantt

|- - - - - - - - - - @plan：点線枠 - - - - - - - - - -| | ■■■■■■ @schedule：バー ■■■■■■ | |- - - - - - - - - - - - - - - - - - - - - - - - - - -| ◆ @due（一点） @due が期間の場合： ◆■■■■■■■■◆ 両端マイルストン＋間を塗りつぶし 仮置き（?）： ░░ 半透明バー ░░ ? 「?」バッジ付き done： 彩度を落とし ✓（バーは実績として残す）
  • plan のみのタスク：点線枠だけを描画（バーなし）。「期間は決めたが日時未定」の状態。
  • due のみのタスク：◆ 単独表示。
  • バリデーションエラー（§3）のタスクは行にエラー印（例：左端に赤ドット）。詳細は Health パネルへ。

2.2 Calendar

@schedule： 通常イベント（タスク=左ボーダー＋チェック余白／予定=枠線／打合せ=塗り） @due： ━━━━━━━━━━◄ 太い横線＋左端に短い矢印終点（「ここまで」感） @plan： データは受け取るが描画しない（将来検討・prop 予約のみ） 仮置き（?）： 半透明＋?バッジ（種別問わず）
  • イベント種別（Q6 確定）：チェックボックスなし＋@schedule ＝「予定」。予定のうちタグが「打合せ」または「meeting」（設定で追加・変更可）＝「打合せ」。チェックボックス付き＝タスク。
  • calendar-lib は plan prop を受け取るインターフェースだけ先に定義しておく（描画は実装しない）。後から表示を足すときにホスト側の変更が不要になる。

2.3 Editor（装飾）

  • 3 メタと ? をハイライトで区別（例：plan=点線下線、schedule=実線、due=強調色、?=黄系）。
  • Q1 確定：ファイル上は正規形のみ。入力補完で @s→@schedule: 等に展開（issue-phase003-008 に統合）。表示上の圧縮（アイコン化）は E-1 のモック段階で判断。

3. バリデーションと継承の仕様（確定）

規則内容重さ提示先
V-1plan.start ≤ schedule.start かつ schedule.end ≤ plan.end（schedule が plan 枠に収まる）エラーHealth パネル（新ルール群）＋エディタ lint 印＋ガント行の印
V-2plan.end ≤ due(end)（枠の終わりが期限を超えない）エラー
V-3schedule.end ≤ due(end)（作業予定が期限を超えない）エラー
V-43 メタのいずれも無い未完タスク警告（既存 undated ルールを継続）
  • 入力は禁止しない：エディタで自由に書ける。違反は保存データとして許容し、検知・提示のみ行う（Q2）。
  • plan の継承：自身に @plan が無い場合、最も近い祖先（親タスク／グループ）の @plan を内部値として引き継ぎ、V-1/V-2 の判定に用いる。Markdown へは書き込まない。ビュー上で継承値を使っていることが分かる表示（例：点線枠を薄く）にするかは実装時判断。
  • メタ位置（Q4 確定）：タスク行直下は「推奨＋アプリの正規位置」。自動生成（upsert-meta・ピッカー挿入）は必ず直下に書く。ただし直下でなくても子要素内にあれば正しいメタとして解釈する（パーサーは位置に寛容、ライターは厳格）。位置ずれの一括整形はユーザーがコマンドで明示的に呼んだときのみ実行。lint は「推奨位置でない」を情報レベルで出す程度に留める。

4. Q1〜Q8 決定一覧

Q1　schedule 短縮の方式
決定：入力補完で展開（案 1）。ファイルに残るのは正規形のみ。エイリアスの正式採用はしない。→ issue-phase003-008 のメタ補完に統合。
Q2　時間メタの意味論
決定：§1 の 3 層モデル＋? 修飾子（全メタ適用可）。3 メタのいずれか 1 つ必須。順序制約 plan.start ≤ schedule ≤ plan.end ≤ due(end) はエラー提示（入力禁止はしない）。plan は祖先から内部継承（Markdown 自動追記なし）。due は期間も可。plan は calendar 非表示（データは受領）。※ schedule の名称は再考中（§7）。
Q3　@plan の精度・グループ付与
決定：日時精度は任意（日付のみ＝終日解釈）。グループにも 3 メタすべて付与可。
Q4　メタ位置規約
決定：直下は推奨＋自動生成の正規位置。子要素内なら位置を問わず有効。 一括フィックスはユーザーがコマンドを呼んだときのみ。
Q5　gantt サブタスク DnD の詳細
決定：提案どおりで OK（デフォルト期間長・ネスト表示は実装時にエンジニア裁量。初期案：デフォルト 1 時間＋その場リサイズ、ネストは全展開）。
Q6　予定・打合せの判定
決定：チェックボックスなし＋@schedule＝「予定」。タグ「打合せ」「meeting」（設定で追加・変更可）＝「打合せ」。
Q7　祝日リストの持ち方
決定：設定画面で設定ファイルのパスを指定する方式。デフォルトパスは main.js と同じディレクトリ（プラグインフォルダ）。※ 2026 年版の祝日テンプレ同梱は引き続き推奨。
Q8　ライブラリ 3 リポジトリの Issue 管理
決定：独立管理。本リポジトリで Issue をとりまとめ（要件を確定）→ 各ライブラリリポジトリで個別に実装 Issue 化する 2 段構え。

5. 決定を反映した実装計画（リポジトリ別）

Q8 の決定により、本体リポジトリの Issue には「ライブラリへ渡すインターフェース（prop/コールバック）仕様の確定」までを含め、描画実装は各ライブラリの Issue に切り出す。境界を明確にするため、リポジトリ別に整理する。

5.1 本体（markdownEditor-for-mywork）

Step 1：記法 Spec 起票＋パーサー ├ 時間メタ 3 層モデル Spec（§1〜§3 を元に日本語で起票。schedule 名称もここで確定） ├ remark-meta-fields：@plan 追加・? 修飾子・due 期間対応 ├ schedule-normalize：plan/due への省略記法適用 ├ viewmodel：plan 継承の解決（祖先探索） └ Health：V-1〜V-3 エラールール＋ tentative-near ルール追加 Step 2：ast-to-* とライブラリ IF 確定 ├ ast-to-gantt / ast-to-calendar / ast-to-kanban に新 prop を追加 │ gantt item: { plan?, tentative?, milestone?(due), status, trailingLabels[] } │ calendar item: { kind: task|event|meeting, due?, plan?(予約のみ), tentative? } │ kanban card: { breadcrumb: string[] } ├ 共通設定：祝日ファイル参照（デフォ＝プラグインフォルダ）・weekend・表示パラメータ・meeting タグ └ ライブラリへの要件 Issue をここで確定 → 各 lib リポジトリへ Step 3：エディタ ├ 003-008 拡張：メタ補完（@s→@schedule）＋期間デートピッカー（挿入は省略形・正規位置） ├ 装飾強化：3 メタ・?・見出しのハイライト（モック先行） └ lint：? 位置検査／メタ推奨位置（情報レベル）／一括整形コマンド（明示呼び出しのみ）

5.2 gantt-lib（../ganttchart-for-mywork）— 改修が最多

  • plan 点線枠／due ◆（期間は ◆〜◆ 塗り）／tentative 半透明＋?／done 彩度落とし＋✓
  • trailingLabels（バー右の汎用ラベル配列）
  • weekend/holidays prop によるヘッダ・列の色替え
  • 左パネル：indentWidth / panelWidth の prop 化＋縮小デフォ＋リサイズ記憶
  • サブタスク表示（折り畳み・期間なし行・行 DnD→onSchedule コールバック）※ Unscheduled Tray（003-001）とコールバック仕様共通化

5.3 calendar-lib（../calendar-for-mywork）

  • kind（task/event/meeting）の描き分け：左ボーダー／枠線ゴースト／塗り
  • due の「太い横線＋左端矢印」描画
  • plan prop の受け口だけ定義（描画なし）
  • tentative 半透明＋?／weekend・holidays の色替え

5.4 kanban-lib（../kanban-for-mywork）

  • 最優先 サブカードグループ DnD ドロップ位置バグ（issue-phase003-012 差し戻し分）

7. 残っている論点（少数）

  • R-1（唯一のブロッカー）：@schedule の名称 — 「意思表示・時間ブロック」の意味に合う名前に変えるか、現状維持か。候補：@do / @work / @slot / @focus / 現状維持。Spec 起票（Issue #1）までに確定が必要。既存ファイルの移行は lint 一括変換で対応可能。
  • R-2：plan 継承値のビュー上の見せ方（継承した点線枠を薄く表示するか、非表示か）— 実装時判断で可。
  • R-3：calendar での @plan 表示 — 将来検討（今回は prop 予約のみ）と決定済み。検討再開のトリガー（例：週ビュー実装時）だけ決めておくと忘れない。
  • R-4：Q5 詳細（DnD デフォルト期間長・ネスト表示）はエンジニア裁量と決定。初期案（1 時間・全展開）で実装し、使用感で調整。
