0. 整理の考え方 — 3 つのレイヤーに分解する

提示された改善項目はビュー別に書かれているが、実装の観点では「どのレイヤーに手が入るか」で分類し直すと検討しやすい。本プロダクトは 3 レイヤー構成である：

レイヤー実体変更の重さ
記法/パーサー本リポジトリ src/lib/parser/（meta-keys・remark プラグイン・normalize）最重。全ビュー・lint・patch・テストに波及。Spec 起票必須。後方互換に注意
ホスト本リポジトリ（ast-to-* 変換・設定・エディタ装飾・patch）中。ビュー単位で閉じる
ライブラリ別リポジトリ ../calendar-for-mywork / ../ganttchart-for-mywork / ../kanban-for-mywork（file: 参照）中。汎用性を保つのがライブラリ方針（kaisou 構想メモ）なので、md 固有概念を持ち込まず prop で渡す設計にする

今回の項目を分類すると、記法レイヤーに触るものが 4 つ（仮置き ?・@plan・schedule 短縮・メタ位置規約）あり、これらは全ビューの前提になるため最初に仕様を確定すべき。逆にガント・カレンダーの見た目系はライブラリ側で独立に進められる。

記法レイヤー（先に決める） ├ 仮置き予定 @schedule?: → 全ビューの描画・Health に波及 ├ 新メタ @plan（この期間でやる枠） → gantt 点線枠・Health に波及 ├ schedule 短縮記法 → lint・補完・正規化に波及 └ メタ行の位置規約（タスク行直下） → lint・upsert-meta に波及 共通設定（ホスト） └ 祝日・週末定義 / 表示パラメータ設定 → gantt・calendar 両方へ prop で配布 ビュー個別（並行可能） ├ editor：ハイライト強化・日付ピッカー ├ gantt：サブタスク表示・マイルストン・done 表現・左パネル ├ calendar：種別の視覚区別 └ kanban：DnD バグ修正・親カード/ユニットのラベル表示

1. 横断テーマ A：記法の拡張（最初に決めるべきもの）

A-1. 仮置き予定 — メタキー末尾の ?

要望 記法gantt/calendar

@schedule?: 2026-07-10T10:00/12:00 のように ? を付けたら「仮置き」。ガントでは透明度を上げ「?」マークを表示。

実装方針：remark-meta-fields でキー末尾の ? を検出し、値は通常どおりパース、Meta 型に tentative: { schedule?: true, due?: true, ... } を追加（キーごとに保持すれば @due?: にも自然に拡張できる）。ast-to-* 変換で tentative フラグをライブラリの item prop へ渡し、描画（半透明＋?バッジ）はライブラリ側。書き戻し（ドラッグ移動）時は ? を保持する必要があるため upsert-meta／markdown-patch の対応が必須。lint は「? はキー直後のみ有効」を検査。
追加提案①：仮置きの「確定操作」を用意する — ガント/カレンダーのイベント右クリックまたは編集ダイアログに「確定」ボタンを置き、? を外す書き戻しを行う。手でエディタに戻って ? を消す運用だと仮置きが放置される。
追加提案②：Health に新ルール「tentative-near：仮置きのまま開始が N 日以内に迫っている」を追加。仮置きの放置は「いつやるか未確定」問題（P2）の再発なので、検知まで含めて一つの機能とみなすのが良い。

A-2. 新メタ @plan — 「この期間内でやる」枠

要望 記法gantt

「この間でこのタスクをやる」を点線枠で表現。schedule バーを枠が包むイメージ。

実装方針：META_KEYS に plan を追加。値は @schedule と同じ期間形式（2026-07-07/07-11）で、schedule-normalize の省略記法をそのまま流用。ガントへは task item に plan?: {start,end} を渡し、ライブラリ側でバーの背後に点線フレームを描画する。日単位精度で十分（時刻は不要）と思われるが要確認（§9）。
追加提案①：意味論を「plan ⊇ schedule」と定義し、Health に「schedule が plan 期間からはみ出している」検査を追加する。枠の意味がツールに理解されていると、単なる飾りではなく計画の整合性チェックになる。
追加提案②：@schedule 未設定で @plan だけのタスクを「粗い予定あり」として扱い、Agenda の undated から除外／ガントでは点線枠のみ表示。これで「週は決めたが日時未定」という現実によくある状態を表現できる（仮置き ? との使い分け：?＝日時はあるが自信なし、@plan のみ＝日時そのものが未定）。

A-3. 「schedule」が長い — 短縮記法

要望 記法editor

毎回 @schedule: と打つのは長い。

実装方針（2 案）：
案 1：入力だけ短くする（推奨） — ファイルに残る正規形は @schedule のまま、エディタ補完で @s→@schedule: に展開（issue-phase003-008 のメタ補完に統合）。パーサー・lint・他ツールとの互換に一切影響しない。
案 2：エイリアスを正式採用 — @sch: / @s: をパーサーが受理（meta-keys にエイリアステーブル追加）。ファイル上も短くなるが、正規形が 2 つになり lint・grep・可読性のコストを恒久的に払う。採用するなら「lint のクイックフィックスで正規形へ揃える／揃えない」を設定にする必要がある。
提案：まず案 1 で運用し、それでも「読むときも長くて邪魔」が残るなら、エディタ装飾（A-4/E-1）で @schedule: を 📅 等に表示上だけ置換する（Obsidian の Live Preview 的アプローチ）。データは長く・見た目は短く、が最も安全。

A-4. メタ行の位置規約 — タスク行の直下に置く

要望 記法lint/patch

ネストタスクのメタ情報（@schedule など）はタスク記載行の直下に置く、を規約化したい。

実装方針：これは新機能というより記法 Spec への規約追加＋lint ルール化。①Spec に「メタ行はタスク行直下に連続して置く（サブタスク・メモより前）」を明記、②notation-lint に「メタ行がサブタスクの後にある」警告＋クイックフィックス（直下へ移動）を追加、③upsert-meta の挿入位置ロジック（現状 taskIdx+1 から走査）がこの規約と一致しているかテストで固定。
要確認：現状パーサーは「サブタスクの後に書かれたメタ」を拾ってしまうのか、無視するのか。拾う場合、規約化後に既存ファイルが警告だらけにならないよう、クイックフィックスの一括適用（ファイル単位）もセットで用意したい。

2. 横断テーマ B：共通設定

B-1. 週末・祝日の色分け（gantt / calendar 共通）

要望 設定gantt/calendar

日付ヘッダの土日の色を変える。ユーザー定義の祝祭日も指定でき、その日も色を変える。ガント・カレンダー両方。

実装方針：ホスト設定に「週末とみなす曜日（デフォ土日）」と「祝日リスト」を持ち、両ライブラリへ holidays: string[]（YYYY-MM-DD）＋weekend: number[] の prop として配布。ライブラリ側はヘッダ・列背景の色替えのみ実装（祝日の意味は知らない＝汎用性維持）。祝日リストの持ち方は、設定 UI での手入力よりVault 内の markdown/JSON ファイル（例 holidays-2026.md）を指定して読む方が、年次更新・共有・Git 管理に向く。
追加提案：日本の祝日は年ごとに官報で確定する固定リストなので、「内閣府 CSV から変換した 2026 年版をテンプレートとして同梱」しておくと導入即使える。将来 ics 購読（前レポート §7.4）を入れるなら祝日 ics もそこに統合できるため、データ形式は ics 互換の日付配列にしておくと二度手間がない。

B-2. バー横の表示パラメータ設定（gantt）

要望 設定gantt

タスク名の横に期間情報のほかステータス等を表示。表示するパラメータは設定で変更できる（デフォはステータスのみ）。

実装方針：ライブラリは「バー右側に任意のラベル配列を描く」汎用 slot/prop（trailingLabels: {text, kind}[]）だけ持ち、何を出すかはホストが組み立てる。ホスト設定に表示項目のチェックリスト（status / due / priority / tags / progress…）を置き、ast-to-gantt で文字列化して渡す。この分担なら将来「進捗率を出したい」等が設定追加だけで済む。

3. Editor の改善

E-1. ハイライトの工夫（メタ・見出し）

要望 editor 装飾

メタ情報や H1 要素などをもっと見やすくハイライトしたい。

実装方針：task-decoration.ts（CM6 装飾）の拡張。具体案：①メタ行はキー部分をバッジ風（背景色つき角丸）に、値の日付部分を等幅で強調、②H1〜H3 は文字サイズ／下線で段階付け、③ステータス記号 [>]/[!] は色分け（doing=青、blocked=赤系）を行全体の淡い背景にも反映。先にモック（スクリーンショット合成）で見た目を合意してから実装することを推奨 — 装飾は好みの差が出やすく、作り直しが多い領域。
追加提案：A-3 と統合し「表示上の圧縮」もここで扱う（@schedule:→アイコン化、カーソルが乗ったら生テキスト表示）。また仮置き ?（A-1）は黄色系、@plan（A-2）は点線下線など、新記法の装飾を記法実装と同じ Issue に含めると抜けがない。

E-2. 期間入力のデートピッカー

要望 editor 既存 issue-phase003-008 と統合

@schedule などの期間入力系に、素早く入力できるデートピッカーをアシスト表示。

実装方針：open 中の issue-phase003-008（メタ補完・日付ピッカー）がそのまま該当。今回の要望で加わる要件は「期間（start/end）を 1 つの UI で入れる」こと — カレンダーポップオーバーで開始日クリック→終了日クリック→時刻はテキスト（10:00-12:00）が最速。既存の省略記法（26-07-10T10/12:30 等は normalize が展開）を活かし、ピッカーは省略形のまま挿入するとファイルが冗長にならない。

4. Gantt の改善

G-1. 左パネルのスリム化

要望 gantt-lib

左パネルのデフォルトインデントをもっと短く。パネル幅ももっと短く。

実装方針：ライブラリの定数を prop 化（indentWidth・panelWidth、デフォルト値を現状より縮小）し、ホスト設定から渡す。パネル幅はドラッグでリサイズ＋記憶があると調整不要になる。小さいが体感効果の大きい改善なので、G 系の先頭で消化するのが良い。

G-2. サブタスクの概念（折り畳み・期間なしサブタスク・その場 DnD）

要望 gantt-libast-to-gantt — 今回最大の機能

デフォ OFF のサブタスク表示。期間なしでも成立し、親バーの下にリスト表示。文字を DnD するとその場で期間設定できる。親タスク単位で折り畳み。

■■■■■■■ 親タスク ■■■■■■■ |・サブA ← 期間なし：行として表示 |　 ■■ サブB ■■ ← 期間あり：バー表示 |・サブC ← 行を DnD → @schedule が書き込まれてバー化
実装方針：AST は既に親子（TaskNode.children）を持つため、ホスト側は「サブタスクを畳んで range 集約」（現状の descendantDateRange）に加え「展開して個別 item として渡す」モードを追加するだけ。ライブラリ側が本丸で、①行の親子関係と折り畳み（デフォ collapsed／表示自体デフォ OFF）、②期間なし item は「チャート領域に左寄せのテキスト行」として描画、③そのテキストをタイムライン上へドラッグしたら onSchedule(itemId, start, end) をコールバック → ホストが upsert-meta で @schedule を書き戻し。これは Unscheduled Tray（issue-phase003-001）の「未予定→ドラッグで予定化」とコールバック仕様を共通化すべき — 同じ「無から期間を作る」操作が 2 箇所にできるため。
要確認：ドラッグで作る期間のデフォルト長（例：1 時間？その場でリサイズ？）と、ネスト 3 段以上のときの表示（全展開か、直下 1 段のみか）。

G-3. due のマイルストン表示・done の見た目・仮置きの半透明

要望 gantt-libast-to-gantt

① @due はマイルストン（◆）で表示。② done は完了と分かる見た目に。③ 仮置き（A-1）は透明度を上げ「?」マーク。

実装方針：いずれも「item に状態フラグを渡し、ライブラリが描き分ける」パターンで一括設計できる。item prop に milestone?: date / status / tentative を追加し、描画規則は：due=バー右に ◆（バーなしタスクは ◆ 単独）、done=彩度を落として✓（バー自体は残す：実績の記録なので消さない）、tentative=opacity 0.5＋「?」バッジ。@plan（A-2）の点線枠も同じ改修に同乗させると、ライブラリ改修が 1 回で済む。

C-1. 週末・祝日の色分け

→ B-1 に統合（gantt と共通の設定・prop 設計で 1 Issue にする）。

C-2. タスク／打合せ／単純な予定の視覚的区別

要望 記法 or 設定calendar-lib

タスクと打合せと単純な予定が視覚的に分かるように。ただし、うるさいのは NG。

実装方針：まず「打合せ」「単純な予定」を記法上どう表すかの決めが必要（§9）。現実的な案：
種別の判定：①チェックボックス付き＝タスク、②チェックボックスなしのリスト項目＋@schedule＝予定（追うステータスが無いもの）、③予定のうち @tags: 会議 等の指定タグ＝打合せ。タグ→種別のマッピングは設定で定義（「会議/MTG/打合せ → meeting」）。
描き分け（うるさくしない）：色数を増やすのではなく形で区別する — タスク＝左ボーダー＋チェック余白、打合せ＝塗りつぶし、単純予定＝枠線のみ（ゴースト）。色はステータス／タグ由来の 1 系統に留める。
追加提案：前レポート §7.4 の外部カレンダー（ics 読み取り）を入れると「打合せ」は大半がそちら由来になる。その場合「外部予定＝グレー系で固定・編集不可」という区別が自然に生まれるため、種別記法を作り込みすぎる前に ics 連携の時期を決めることを推奨（先に ics が来るなら②③の記法は最小限でよい）。

6. Kanban の改善（バグ含む）

K-1. サブカードグループ DnD のドロップ位置バグ

バグ 要修正kanban-lib

サブカードグループの DnD でドロップ位置がおかしい（座標計算の疑い）。ステータスは変更されるが、カードの表示位置が変わらない。

対応方針：issue-phase003-012（カードグループ、status: implemented・ユーザー動作確認待ち）の確認プロセスで検出された退行とみなし、新規 Issue ではなく 003-012 を差し戻し（open へ）て再現手順を追記するのがガバナンス上素直。「ステータス書き戻しは成功・表示位置のみ不整合」という症状は、書き戻し→再パース→ビュー再構築の経路でカードグループの並び順が再計算されていない（またはネスト時のドロップインデックスがフラットな座標で計算されている）ことを示唆。再現手順・階層構成・期待位置をスクリーンショット付きで Issue に固定してから修正に入ること。

K-2. 非グループ表示時のコンテキスト表示（親カード／ユニット）

要望 ast-to-kanbankanban-lib

① カードグループ表示でないとき、親カードがある場合はセクション欄に親カードを記載。② ユニット表示でないとき、ユニットに属する場合はカードにユニット名も記載。

実装方針：2 件は同型の要望＝「グルーピングを解除しても所属コンテキストを失わない」。カードの prop に breadcrumb: string[]（例 ["セクション", "親カード", "ユニット"]）を渡し、ライブラリはカード下部に小さく セクション › 親カード › ユニット と 1 行表示する設計に一般化すると、①②が 1 実装で済み、将来ファイル横断表示時の「どのファイル由来か」もここに載せられる。表示・非表示と粒度（親カードまで／ユニットまで）は設定。
