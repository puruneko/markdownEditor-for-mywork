## 1. 目的

本プロダクトのオーナーは「タスクの期限（いつまで）と実施予定（いつやるか）の管理不全」を根本課題として本アプリを開発している。単一の日時メタでは「バッファを含めた予定枠」「今この時間にやるという意思表示」「締め切り」という3つの異なる意味を区別できず、ビュー間で解釈が食い違う原因になっていた。

本 Spec は、時間表現を `@plan` / `@schedule` / `@due` の3層＋横断修飾子「仮置き `?`」として体系化し、パーサー・バリデーション・各ビューの描画・エディタ装飾が同一の意味論に基づいて動作することを保証する。

本 Spec は 2026-07-03 のオーナー決定（`project/plan/time-meta-spec-and-implementation-plan-2026-07-03.html` §1〜§3、Q1〜Q8）を正式な Spec として起票したものであり、内容の新規発明は行っていない。

---

## 2. 適用範囲

含む:
- `@plan` / `@schedule` / `@due` の意味論・値形式・省略記法
- `?`（仮置き）修飾子の構文・適用範囲
- バリデーション規則 V-1〜V-4
- `@plan` の祖先継承
- メタ行の推奨位置とパーサー／ライターの寛容度・厳格度の非対称性
- Gantt・Calendar 各ビューの描画仕様（意味レベル）
- ライブラリ（gantt/calendar/kanban）と本体の責務境界
- エディタ装飾の対象

含まない（詳細は「8. 対象外」参照）:
- `@schedule` のキー名変更
- Health パネルの個別ルール実装、ast-to-* の prop 型定義、共通設定の実装詳細
- 視覚デザインの色・線幅等の具体値

## 3. 定義

- **3層モデル**: `@plan`・`@schedule`・`@due` の3つのメタキーからなる時間表現の体系。
- **@plan**: 「この期間の中でタスクを実施しなければならない」というバッファ込みの予定枠（WBS 的な意味）。
- **@schedule**: 「この時間に私はこの作業をする」という意思表示（時間ブロック）。既存のメタキーであり、本 Spec では名称を変更しない（8章参照）。
- **@due**: 「ここまでにタスクを終わらせる」という期限。
- **仮置き（tentative）**: メタキー直後に付与する `?` 修飾子。そのメタの値が未確定であることを示す。
- **継承**: 自身に `@plan` を持たないタスクが、最も近い祖先タスク／グループの `@plan` を内部値として参照すること。Markdown への書き込みを伴わない。
- **メタ行**: タスク行の子要素として記述される `- @key: value` 形式の行。
- **推奨位置**: メタ行がタスク行の直後（連続する最初の子要素）に置かれている状態。
- **意味を持たない prop**: `@plan` や「祝日」等ドメイン概念を含まない、単なる値の入れ物としての prop（例: `plan?: {start, end}`, `holidays: string[]`）。

## 4. 振る舞い要件（BEHAVIORAL REQUIREMENTS）

### 4.1 3層モデルの基本

BR-001 タスクは `@plan`・`@schedule`・`@due` のいずれか1つ以上を持たなければならない。

BR-002 `@plan` は「この期間内でタスクを実施しなければならない」というバッファを含む予定枠を表さなければならない。

BR-003 `@schedule` は「この時間にこの作業をする」という意思表示（時間ブロック）を表さなければならない。

BR-004 `@due` は「ここまでにタスクを終わらせる」という期限を表さなければならない。

BR-005 `@due` の値は一点日付または期間のいずれでも指定できなければならない。

BR-006 `@plan` の値が日付のみの場合は終日（00:00〜23:59）と解釈しなければならない。ただし、この終日展開はパーサー層で行ってはならず、投影層（ast-to-*、issue-phase004-004 の対象）が行わなければならない。

BR-007 子にタスクを持つグループ（親タスク）にも `@plan`・`@schedule`・`@due` のすべてを付与できなければならない。

### 4.2 仮置き修飾子

BR-008 `?` 修飾子は、メタキー名の直後・コロンの前にのみ記述できなければならない（正: `@schedule?:`）。

BR-009 `?` 修飾子は `@plan`・`@schedule`・`@due` の3メタに付与できなければならない。

BR-010 `?` 修飾子付きのメタは「仮置き」を意味し、全ビューにおいて半透明表示および「?」バッジにより仮置きであることを示さなければならない。

BR-011 `?` の位置が BR-008 に反する場合（例: `@schedule ?:` や `@?schedule:`）、そのメタ行は不正なメタとして扱わなければならない。

### 4.3 値の省略記法

BR-012 `@plan` と `@due` の値には、`@schedule` と同じ省略記法（2桁年展開・分省略・継続省略）を適用しなければならない。

### 4.4 バリデーション

BR-013（V-1） `@schedule` を持つタスクは、`schedule` が `plan` 枠に収まらなければならない（`plan.start ≤ schedule.start` かつ `schedule.end ≤ plan.end`）。

BR-014（V-2） `@plan` と `@due` を両方持つタスクは、`plan.end ≤ due(end)` でなければならない。

BR-015（V-3） `@schedule` と `@due` を両方持つタスクは、`schedule.end ≤ due(end)` でなければならない。

BR-016 BR-013〜BR-015 の違反は、エラーとして提示しなければならない。ただし、違反する値の入力そのものを禁止してはならない。

BR-017 `@plan`・`@schedule`・`@due` のいずれも持たない未完了タスクは、警告として提示しなければならない（既存の undated ルールを継続する）。

### 4.5 継承

BR-018 タスクが `@plan` を持たない場合、最も近い祖先タスク／グループの `@plan` を内部値として継承しなければならない。

BR-019 継承した `@plan` の値を Markdown へ自動追記してはならない。

BR-020 継承した `@plan` の内部値は、BR-013・BR-014 の判定に使用しなければならない。

### 4.6 メタ行の位置

BR-021 メタ行は、タスク行直下（連続する最初の子要素）に記述することを推奨位置とする。

BR-022 パーサーは、メタ行がタスクの子要素内にあれば、位置（直下か否か）を問わず受理しなければならない。

BR-023 メタの自動書き込み（`upsert-meta`・日時ピッカーからの挿入等）は、必ずタスク行直下に書き込まなければならない。

BR-024 メタ行の推奨位置への一括整形は、ユーザーが明示的にコマンドを呼び出した場合にのみ実行しなければならない。ファイル保存時・編集時の自動実行をしてはならない。

BR-025 一括整形コマンドは冪等でなければならない。同じファイルに対して2回連続で実行した場合、2回目は変更を発生させてはならない。

BR-026 メタ行が推奨位置にない場合、lint はこれを情報レベル（error・warning より弱いレベル）で提示しなければならない。警告レベルで提示してはならない。

### 4.7 描画仕様 — Gantt

BR-027 Gantt は `@plan` を点線枠として描画しなければならない。

BR-028 Gantt は `@schedule` をバーとして描画しなければならない。

BR-029 Gantt は `@due` が一点の場合、◆として描画しなければならない。

BR-030 Gantt は `@due` が期間の場合、両端に◆を配置し、間を塗りつぶして描画しなければならない。

BR-031 Gantt は仮置き（`?`）のメタを半透明表示＋「?」バッジで描画しなければならない。

BR-032 Gantt は `done` ステータスのタスクを、彩度を落とし✓付きで描画しなければならない。

### 4.8 描画仕様 — Calendar

BR-033 Calendar は `@schedule` をイベントとして描画しなければならない。

BR-034 Calendar は `@due` を太い横線＋左端矢印として描画しなければならない。

BR-035 Calendar は `@plan` のデータを受け取らなければならないが、描画してはならない（将来検討・prop 予約のみ）。

BR-036 Calendar は、チェックボックスを持たず `@schedule` を持つノードを「予定」として扱わなければならない。

BR-037 Calendar は、「予定」のうち tags に「打合せ」または「meeting」（設定で追加・変更可能）を含むものを「打合せ」として扱わなければならない。

BR-038 Calendar は、チェックボックスを持つノードを「タスク」として扱わなければならない。

### 4.9 責務境界

BR-039 gantt・calendar・kanban の各ライブラリは、`@plan` や「祝日」等のドメイン意味を持ち込んではならず、意味を持たない prop（例: `plan?: {start, end}`、`holidays: string[]`）のみを受け取って描画しなければならない。

BR-040 Markdown からライブラリ prop への意味解釈は、すべて本体（ast-to-*）が行わなければならない。ライブラリはこれを行ってはならない。

### 4.10 エディタ装飾

BR-041 エディタは `@plan` を既存メタキーと同様の装飾クラスでハイライトしなければならない。

BR-042 エディタは仮置き（`?`）修飾子付きのメタを、通常のメタと視覚的に区別可能な装飾クラスでハイライトしなければならない。

BR-043 既存の設定トグル（`enableTaskHighlight`）を OFF にした場合、BR-041・BR-042 の装飾および関連する lint はすべて無効化されなければならない。

## 5. 非振る舞い制約（NON-BEHAVIORAL CONSTRAINTS）

- メタキー名は本 Spec の適用範囲内では変更しない（8章参照）。
- ライブラリ（gantt/calendar/kanban）は本体から独立した汎用ライブラリとして開発される方針を維持する（意味の解釈を持ち込まない）。
- Markdown が唯一の正の情報源である方針を維持する。一括整形コマンドはタスクの子要素の行順序のみを変更し、本文の非メタ行の内容を変更してはならない。

## 6. 状態モデル

該当なし（本 Spec は状態遷移を持つエンティティを定義しない）。

## 7. 境界条件（EDGE CONDITIONS）

- `@plan` と `@due` のみを持ち `@schedule` を持たないタスクの場合、BR-013（V-1）の判定は対象外としなければならない（`schedule` が存在しないため）。
- 祖先が複数段ある場合、直近（最も近い）の `@plan` を持つ祖先の値を継承値として使用しなければならない（BR-018）。
- タスク自身と祖先の両方に `@plan` がある場合、自身の `@plan` を優先し、祖先の値を継承してはならない。
- `?` の位置が不正な場合（BR-011）、そのメタ行は既存の不正なメタ行と同様に無視しなければならない（値は `meta` に反映されない）。
- `@due` を期間指定した際、終了が開始より前になっている場合、既存の不正な期間指定と同様にエラーとして提示しなければならない。
- `@plan:` のように値が空の場合、不正なメタ行として扱わなければならない。
- `@plan?:` のように `?` 付きで値のみ空の場合も、不正なメタ行として扱わなければならない。

## 8. 対象外（OUT OF SCOPE）

- **`@schedule` のキー名変更（R-1）**: `project/plan/time-meta-spec-and-implementation-plan-2026-07-03.html` §7 の R-1 は本 Spec 起票時点でオーナーの最終回答が得られていない唯一の残論点である。`issue-phase004-000` §2-4 の規定「メタキー名は変えない。全 Issue は現行名で実装する」に従い、本 Spec 及び全ての phase004 実装は現行名 `@schedule` のまま行う。名称変更が決定した場合は、別 Issue（lint 一括変換を含む）で扱う。
- Health パネルの個別バリデーションルールの実装（`issue-phase004-003` の対象）。
- `ast-to-gantt` / `ast-to-calendar` / `ast-to-kanban` の prop 型定義の確定、共通設定（祝日ファイル参照・meeting タグ・表示パラメータ）の実装（`issue-phase004-004` の対象）。
- 視覚デザインの詳細（色・線幅等の具体値）。モック合意後に別途決定する（`project/plan/ux-improvement-proposals-2026-07-03.html` E-1）。
- `@plan` 継承値のビュー上の見せ方（R-2、点線枠を薄くする等）。実装時判断とする。
- Calendar での `@plan` 表示の実現（R-3）。将来検討。
- gantt サブタスク DnD のデフォルト値詳細（R-4、デフォルト期間長・ネスト表示）。実装時判断とする。

## 10. 変更管理（CHANGE CONTROL）

本 Spec の変更は、必ず関連する Issue を参照して行わなければならない。Issue 参照のない直接編集は禁止する。AI は本 Spec を暗黙に拡張してはならない。

R-1（`@schedule` 名称）が確定した場合、本 Spec の DEFINITIONS・8章を更新し、履歴として変更前の記述を削除せず追記すること（`project/governance/NAMING_AND_ID_RULES.md` §5・§6 準拠）。
