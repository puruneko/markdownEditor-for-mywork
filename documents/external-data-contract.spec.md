## 1. 目的

ホスト（Markdown ベースのタスク管理エディタ）は、ユーザーが書いた Markdown を解析し、その結果を連携アプリ（カレンダー、ガントチャート、かんばん等の表示・操作アプリ）へ渡して表示させている。

連携アプリを新たに開発する場合、開発者および AI は「ホストから何が、どの形で、どういう意味で渡されるか」を正確に知らなければならない。本 Spec はその唯一の参照先である。

本 Spec は、**現時点のホスト実装が実際に渡しているデータ**を記述する。将来の構想・未実装の機能を規範として記述しない。実装が未確定である箇所、実装どうしで解釈が食い違っている箇所は、断定せず「注釈（A-01 形式）」として明示する。

本書を読んだ開発者は、Markdown 文字列を自前で解析することなく連携アプリを実装できなければならない。

---

## 2. 適用範囲

含む:

- ホストが連携アプリへ渡すデータ構造（`Document`）の全フィールドと、その値の意味
- 受け渡しの経路・タイミング・更新通知
- 既存の連携アプリ（カレンダー、ガント、かんばん、アジェンダ）が実際に受け取っている値
- 連携アプリから Markdown への書き戻し経路
- エディタから連携アプリへのドラッグ＆ドロップのペイロード
- 識別子の生成規則と、その安定性の限界
- 未確定事項・未実装機能の注釈

含まない（詳細は「8. 対象外」参照）:

- プロセス外通信（HTTP・IPC・ファイル出力）のためのシリアライズ形式
- 表示仕様（色・レイアウト・操作感）
- 連携アプリ内部の実装
- Markdown 記法そのものの設計判断

## 3. 定義

### 3.1 用語

- **ホスト**: Markdown を解析し、連携アプリをマウントする側。Obsidian プラグインとして動作する。
- **連携アプリ**: ホストにマウントされ、解析結果を表示・操作するアプリ。ホストとは別パッケージとして開発される。
- **vault**: ホストが管理する Markdown ファイル群のルートディレクトリ。
- **ソース**: 1個の Markdown ファイルと、その解析結果のペア。
- **Document**: 1ファイルの解析結果。セクションとノードの木構造。
- **セクション**: Markdown の見出し（`#`〜`######`）に対応する要素。
- **ノード**: Markdown のリスト行または引用ブロックに対応する要素。`task`・`list`・`quote` の3種。
- **メタ**: タスク行の子として書かれた `- @キー: 値` 行から取得した付加情報。
- **localId**: 1ファイル内で一意なノード識別子。
- **globalKey**: `<ファイルパス>::<localId>`。複数ファイル横断で一意な識別子。
- **投影**: `Document` から連携アプリ固有の型への変換。ホスト側が行う。
- **仮置き**: メタの値が未確定であることを示す状態。記法上は `?` で表す。

### 3.2 元になる Markdown 記法

連携アプリは Markdown を直接解析しないが、値の由来を理解するために記法を把握しておく必要がある。ホストが解析する記法は次のとおりである。

```markdown
# 総務 2026年6月                      ← セクション（見出し）

## 【清掃業者対応】                    ← 下位セクション

> 連絡先は松田さん。                   ← 引用（quote）：補足・経緯のメモ

- 6月定期清掃 日程変更対応              ← チェックボックス無し行（list）
  - @plan: 26-06-01/30                ← メタ（この行はノードにならない）
  - [>] 松田さんへ日程変更の連絡        ← タスク（task）。`[>]` は進行中
    - @schedule?: 26-06-10T09:00/09:30 ← メタ。`?` は仮置き
    - @due: 2026-06-15
    - @tags: 総務, 清掃
    - @priority: 1
    > 折り返し待ち。                    ← タスクの子の引用（quote）
```

ステータスマーカーの意味は次のとおりである（統一Markdownデータ仕様の7状態モデル。`issue-phase005-001`）。

| 記法 | 値 | 意味 |
|---|---|---|
| `- [?]` | `planning` | 計画中（内容・順序・日時が未整理） |
| `- [ ]` | `ready` | 未着手（実行可能だが未開始） |
| `- [x]` | `done` | 完了 |
| `- [>]` | `in_progress` | 進行中・対応中・相手の回答待ち |
| `- [!]` | `waiting` | 待ち（外部条件の待ち） |
| `- [/]` | `deferred` | 一時保留（自分の都合による後回し） |
| `- [-]` | `cancelled` | 中止（実施しないが流れを残す） |

### 3.3 時間メタ3層モデルの意味

ホストは時間を3つの異なる意味に分けて扱う。連携アプリはこの区別を保ったまま表示しなければならない。

| メタ | 意味 |
|---|---|
| `@plan` | 「この期間の中で実施する」というバッファを含んだ予定枠。作業の外枠であり、実際に手を動かす時刻ではない。 |
| `@schedule` | 「この時間にこの作業をする」という意思表示。実際に時間を確保したブロックを表す。 |
| `@due` | 「ここまでに終わらせる」という期限。一点でも期間でも指定できる。 |

`?`（仮置き）はこの3つに付けられる横断的な修飾であり、「値は入れたが未確定である」ことを意味する。

## 4. 振る舞い要件（BEHAVIORAL REQUIREMENTS）

### 4.1 受け渡しの単位と経路

BR-001 ホストは、連携アプリへソースの配列を渡さなければならない。各ソースは次の構造でなければならない。

```ts
type SourceEntry = {
  path: string    // vault ルートからの相対パス。区切りは '/'
  doc: Document   // 当該ファイルの解析結果
}
```

BR-002 ホストは、連携アプリのマウント用コンポーネントへ次の5項目を props として渡さなければならない。

```ts
interface ViewMountProps {
  /** 表示対象のソース一覧 */
  sources: SourceEntry[]
  /** 更新受け取り用の関数を登録する。連携アプリは初期化時に必ず呼ぶ */
  registerUpdater: (fn: (sources: SourceEntry[]) => void) => void
  /** アイテムがクリックされたことをホストへ通知する。ホストはエディタの該当行へカーソルを移動する */
  onNodeClick: (globalKey: string) => void
  /** Markdown への書き戻しを依頼する（4.8 参照） */
  onNodePatch: (globalKey: string, patcher: (md: string, doc: Document, node: TaskNode) => string) => Promise<void>
  /** 全対象ファイルの再解析を依頼する */
  onReload: () => void
}
```

BR-003 データはプロセス内のオブジェクト参照として渡さなければならない。ホストは受け渡しに際してシリアライズを行ってはならない。

> **注釈 A-01（受け渡し形式）**: 現行の連携方式は「同一プロセス内のパッケージへ props を渡す」のみである。別プロセス・別アプリケーションへ渡すためのシリアライズ形式は存在しない。なお `Document.nodeLineMap` は `Map` であり、そのまま `JSON.stringify` すると `{}` になる。プロセス外へ渡す必要が生じた場合、形式は別途定義しなければならない。

BR-004 連携アプリが受け取る `Document` は、ホストのフィルタ適用後の結果でなければならない。連携アプリは、渡された `sources` がファイルの全内容であると仮定してはならない。

BR-005 連携アプリは、`registerUpdater` に更新関数を登録しなければならない。ホストは、対象ファイルの再解析が完了するたびに、登録された関数を新しいソース配列で呼び出さなければならない。

BR-006 ホストは、ファイル変更から再解析までをデバウンスしなければならない。連携アプリは、1打鍵ごとに更新が届くことを前提にしてはならない。

BR-007 `sources` に含まれるファイルの範囲は、ホスト側の設定（vault 全体・特定フォルダ・現在のファイルのみ）で決まる。連携アプリはこの範囲を制御してはならない。

BR-008 連携アプリは、`sources` が空配列である場合、および任意のファイルが途中で消える場合を扱えなければならない。

### 4.2 Document とセクション

BR-009 `Document` は次の構造でなければならない。

```ts
type Document = {
  type: 'document'
  sections: Section[]
  /** ノード id / セクション id → 0 始まりの行番号 */
  nodeLineMap: Map<string, number>
}
```

BR-010 `Section` は次の構造でなければならない。

```ts
type Section = {
  type: 'section'
  id: string               // 'section-0'（匿名）| 'section-<見出しの出現順>'
  depth: number            // 見出しレベル 1〜6。匿名セクションは 0
  title: string            // 見出しテキスト。匿名セクションは ''
  lineNumber: number       // 0 始まりの行番号。匿名セクションは -1
  parentSectionId?: string // 親セクションの id。最上位セクションでは存在しない
  children: Node[]         // このセクションに直属するノード
  subSections: Section[]   // 下位の見出し
}
```

BR-011 `depth` は Markdown の見出しレベルであり、入れ子の深さではない。`##` の直下に `####` が来た場合、その `depth` は 4 でなければならない。

BR-012 下位の見出しは `subSections` に格納しなければならない。`children` に格納してはならない。連携アプリは、セクションの木を再帰的に辿らなければならない。

BR-013 見出しが1個も存在しないファイルの場合、全内容を `id: 'section-0'`・`title: ''`・`depth: 0`・`lineNumber: -1` の匿名セクション1個に格納しなければならない。

BR-014 先頭の見出しより前に内容が存在する場合、その内容を匿名セクション（`section-0`）に格納しなければならない。内容が存在しない場合、匿名セクションを生成してはならない。

BR-015 連携アプリは、`title` が空文字のセクションを、表示上の階層として扱ってはならない。

### 4.3 ノード

BR-016 ノードは `task`・`list`・`quote` の3種でなければならない。それぞれの意味は次のとおりである。

| 種別 | 由来 | 意味 |
|---|---|---|
| `task` | `- [ ]` 等のマーカー付きリスト行 | 実行単位。ステータスを持つ |
| `list` | マーカー無しのリスト行 | 子にタスクを含む場合はグループ（フェーズ・カテゴリ）。含まない場合はメモ |
| `quote` | `>` 行 | 補足・経緯・状況説明。タスクではない |

BR-017 `TaskNode` は次の構造でなければならない。

```ts
type TaskNode = {
  type: 'task'
  id: string
  text: string               // ステータスマーカーを除去した本文。前後の空白は無い
  status: 'planning' | 'ready' | 'in_progress' | 'waiting' | 'deferred' | 'done' | 'cancelled'
  children: Node[]           // 子ノード。メタ行は含まれない
  parentId?: string          // 注釈 A-02
  meta?: Meta                // メタが1個も無い場合はキー自体が存在しない
  lineNumber: number         // 0 始まりの行番号
  hasTaskDescendant: boolean // 子孫にタスクを1個以上持つ（自身は含めない）
  isGroup: boolean           // hasTaskDescendant かつ children が空でない
  isLeafTask: boolean        // children が空である
  isMemo: false              // タスクでは常に false
  depth: number              // セクション直属を 1 とする入れ子の深さ
  path: string[]             // 注釈 A-03
}
```

BR-018 `ListNode` は、`TaskNode` から `status` と `isLeafTask` を除いた構造でなければならない。`isMemo` は、子孫にタスクを持たない場合に `true` でなければならない。

BR-019 `QuoteNode` は次の構造でなければならない。`children`・`meta`・`depth`・`path` を持ってはならない。

```ts
type QuoteNode = {
  type: 'quote'
  id: string
  raw: string                // 引用記号を除いた本文を '\n' で連結した文字列
  parentId?: string          // 注釈 A-02
  lineNumber: number
  hasTaskDescendant: false
  isGroup: false
  isMemo: true
}
```

BR-020 メタ行はノードとして渡してはならない。メタ行は解析時に `children` から除去され、親タスクの `meta` に畳み込まれる。

BR-021 `isLeafTask` は `children` が空である場合にのみ `true` でなければならない。メタ行は除去されるため、メタのみを子に持つタスクの `isLeafTask` は `true` である。一方、引用（`>`）を子に持つタスクの `isLeafTask` は `false` である。

BR-022 `depth` は、セクション直属のノードを 1 とし、子ノードごとに 1 を加算した値でなければならない。

BR-023 `lineNumber` は、ファイル先頭行を 0 とする行番号でなければならない。連携アプリは、この値をユーザーへ表示する場合、1 を加算しなければならない。

BR-024 `children` の要素は、Markdown 内の出現順に並んでいなければならない。

> **注釈 A-02（parentId は常に未設定）**: 3種のノードいずれも型定義に `parentId?: string` を持つが、解析処理はこのフィールドに値を代入していない。実行時は常に `undefined` である。親子関係は `children` の入れ子構造でのみ表現される。連携アプリが平坦な配列（親 id 参照方式）を必要とする場合、木を辿る際に親の識別子を引き回して自前で構築しなければならない。

> **注釈 A-03（path の形）**: `path` は「直近のセクション見出し1個 + 祖先ノードの text + 自身の text」であり、ノード由来の各要素の末尾には兄弟インデックスの添字が付く。

```ts
// 例（「【清掃業者対応】」セクション配下、グループ配下のタスク）
["【清掃業者対応】", "6月定期清掃 日程変更対応[1]", "松田さんへ日程変更の連絡[0]"]
```

> 次の3点に注意しなければならない。(1) 祖先セクションは直近の1段のみで、その上位の見出しは含まれない。(2) 自身の text を末尾に含む。(3) 添字 `[n]` が付く。表示に使う場合、連携アプリまたはホストの投影層で、末尾要素の除去と `[n]` の除去を行わなければならない。

### 4.4 メタ

BR-025 `Meta` は次の構造でなければならない。すべてのフィールドが省略可能である（`issue-phase005-001` により `condition`・`purpose`・`savepoint`・`special_note` の4キーを追加）。

```ts
type Meta = {
  plan?: string        // 予定枠。"開始" または "開始/終了"
  schedule?: string    // 時間ブロック。"開始" または "開始/終了"
  due?: string         // 期限。"開始" または "開始/終了"
  priority?: number    // 小さいほど優先度が高い
  dependsOn?: string[] // 依存先の指定（自由文字列）
  tags?: string[]      // 分類ラベル
  repeat?: string      // 繰り返し規則（RFC5545 の RRULE 本体）
  condition?: string | string[]     // 完了イメージ。単一行なら string、子リストなら string[]
  purpose?: string | string[]       // 目的。単一行なら string、子リストなら string[]
  savepoint?: string | string[]     // セーブポイント。単一行なら string、子リストなら string[]
  special_note?: string | string[]  // 特記事項。単一行なら string、子リストなら string[]
  tentative?: { plan?: true; schedule?: true; due?: true }  // 仮置き
}
```

BR-069 メタキーは、英字のカノニカルキー（`plan`・`schedule`・`due`・`condition`・`purpose`・`savepoint`・`special_note` 等）に加え、次の日本語エイリアスで書かれた `@キー:` 行を受理しなければならない。両者は解析後、`meta` 上は同一のフィールドとして扱わなければならない。ホストは、どちらの表記で書かれたかを保持しない。

| 日本語エイリアス | カノニカルキー |
|---|---|
| `@想定期間` | `plan` |
| `@実施日時` | `schedule` |
| `@期限` | `due` |
| `@完了イメージ` | `condition` |
| `@目的` | `purpose` |
| `@セーブポイント` | `savepoint` |
| `@特記事項` | `special_note` |

BR-070 `condition`・`purpose`・`savepoint`・`special_note` の4キーに限り、値は子リスト（複数行）を取ることができる。`- @キー:` のように値を空にして直下に子リストを書いた場合、子リストの各項目のテキストを `string[]` として `meta` に格納しなければならない。この場合、子リストはノードの `children` に残してはならない（BR-020 と同様の畳み込みを行う）。子リストが無く値が1行で書かれた場合は、他のメタキーと同様に `string` として格納しなければならない。この2キー挙動（子リストの有無）は、上記4キー以外のメタキーには適用してはならない。

BR-026 `plan`・`schedule`・`due` の値は、期間の場合 `<開始>/<終了>` を1本の文字列として保持しなければならない。開始と終了を別フィールドに分解してはならない。

BR-027 日時の表記は `YYYY-MM-DD` または `YYYY-MM-DDTHH:mm` でなければならない。秒は含めない。

BR-028 日時の値は UTC オフセットを含んではならない。連携アプリは、これを実行環境のローカル時刻として解釈しなければならない。

BR-029 ホストは、ユーザーが書いた省略記法を展開してから渡さなければならない。連携アプリは展開後の値のみを受け取る。展開規則は次のとおりである。

| 省略 | 入力例 | 展開後 |
|---|---|---|
| 継続省略（時刻） | `2026-01-01T10:00/11:30` | `2026-01-01T10:00/2026-01-01T11:30` |
| 継続省略（日） | `2026-01-01/02` | `2026-01-01/2026-01-02` |
| 2桁年 | `26-01-01` | `2026-01-01` |
| 分省略 | `2026-01-01T10` | `2026-01-01T10:00` |

BR-030 仮置き（`?`）の情報は `tentative` に格納しなければならない。`plan`・`schedule`・`due` の値そのものに仮置きの情報を含めてはならない。連携アプリは、仮置きのメタを確定値と視覚的に区別しなければならない。

BR-031 `priority` は数値でなければならない。値が小さいほど優先度が高いことを意味する。

BR-032 `tags` および `dependsOn` は、ユーザーがカンマ区切りで書いた値を分割し、各要素の前後空白を除去した文字列配列でなければならない。

BR-033 `dependsOn` の要素は自由文字列であり、ノードの識別子との対応は保証されない。連携アプリは、解決できない依存指定を無視しなければならない。

BR-034 `repeat` は RFC5545 の RRULE 本体でなければならない。`RRULE:` 接頭辞および `DTSTART` を含んではならない。

BR-035 繰り返しの起点は `schedule` の開始時刻でなければならない。各オカレンスの長さは `schedule` の長さと同一でなければならない。

BR-036 ホストが解釈できないキーのメタ行（`@foo:` 等）は、`meta` に現れてはならない。連携アプリは未知のメタキーを受け取らない。

BR-037 同一タスクに同じメタキーが2回以上書かれている場合、最後に書かれた値のみが `meta` に現れなければならない。

> **注釈 A-04（同一キーの複数記述）**: BR-037 は現行実装の挙動である。「1つのタスクに複数の `@schedule` を書ける」仕様にするか否かは未決定である。連携アプリは、当面は1タスクにつき各メタ最大1個として実装しなければならない。

> **注釈 A-05（数値として不正な priority）**: `@priority: high` のように整数へ変換できない値が書かれた場合、`priority` には `NaN` が入る。ホストはこれをエラーとして扱わない。連携アプリは `Number.isNaN()` による確認を行わなければならない。なお `NaN` は JSON で表現できないため、受け渡しの内容を JSON へ書き出した場合は `null` になる。

> **注釈 A-12（値が空のメタ行）**: `@plan:` のように値を書かずにコロンだけで終えたメタ行は、無視されずに空の値として `meta` に現れる。`plan`・`schedule`・`due` は空文字列 `""`、`tags`・`dependsOn` は空文字列1個を含む配列 `[""]`、`priority` は `NaN`、`repeat` は空文字列になる。これを不正入力として扱うか否かは未決定である。連携アプリは、空文字列の日時値を描画してはならない。

> **注釈 A-06（展開されない省略記法がある）**: BR-029 の継続省略は「終端に `-` を含まない」場合にのみ適用される。`26-06-01/06-30` のように終端に月まで書いた値は継続省略と判定されず、2桁年展開だけが適用されて `2026-06-01/2006-30` という不正な値になる。ホストは例外を投げず、警告も出さない。連携アプリは、日時のパースが失敗し得ることを前提に実装し、失敗した値を描画してはならない。

> **注釈 A-07（`@plan` の継承は未実装）**: 時間メタ3層モデルの Spec（`time-meta-model.spec.md`）は「`@plan` を持たないタスクは、最も近い祖先の `@plan` を継承する」と規定しているが、この継承はホスト側に未実装である。現時点の `meta.plan` は、そのノード自身に書かれた値のみである。継承後の値が必要な連携アプリは、`children` の木を自分で遡らなければならない。

### 4.5 識別子

BR-038 ノードの `id`（localId）は、文書内の構造上の位置を連結した文字列でなければならない。生成規則は次のとおりである。

- セクション接頭辞: `s<見出しの出現順>`（匿名セクションおよび先頭見出し前は `s0`）
- ノード: 親の位置パスに `n<兄弟インデックス>` を連結する
- 引用: 親の位置パスに `q<兄弟インデックス>` を連結する
- 例: `s2.n1.n0`（2番目の見出し配下、2番目のノードの1番目の子）、`s2.q0`

BR-039 兄弟インデックスは、メタ行を除去した後の並びで採番しなければならない。

BR-040 セクションの `id` は `section-<見出しの出現順>` でなければならない。ノード id の接頭辞（`s2`）とセクション id（`section-2`）は表記が異なる。

BR-041 `globalKey` は `<path>::<localId>` でなければならない。連携アプリは、複数ファイルを横断する一意キーとしてこれを使用しなければならない。

BR-042 連携アプリがホストへ識別子を返す場合（クリック通知・書き戻し）、受け取った `globalKey` をそのまま返さなければならない。加工した値を返してはならない。

> **注釈 A-08（識別子は永続ではない）**: `id` は文書内の位置から生成されるため、行の追加・削除・並べ替えによって同一タスクの `id` が変化する。連携アプリは、`id` や `globalKey` を、データベースの主キー・ユーザー設定の保存キー・ブックマークとして使用してはならない。1回の受け渡しの中でのみ有効な参照として扱わなければならない。編集に耐える恒久識別子はホスト側に存在しない。

### 4.6 責務境界

BR-043 Markdown の意味の解釈（時間メタ3層モデル、祝日、打合せ判定等のドメイン概念）は、すべてホスト側が行わなければならない。連携アプリがこれを行ってはならない。

BR-044 連携アプリは、ドメイン的な意味を持たない汎用的な prop のみを受け取る形で設計しなければならない（例: `plan?: { start, end }`、`holidays: string[]`）。prop 名に業務語彙を持ち込んではならない。

BR-045 連携アプリは、Markdown 文字列を自前で解析してはならない。

BR-046 連携アプリは、ホストのファイル入出力 API に直接アクセスしてはならない。ファイル操作は `onNodePatch` および `onReload` のみを経由しなければならない。

BR-047 連携アプリは Shadow DOM 内にマウントされる。グローバル CSS セレクタに依存してはならない。

### 4.7 既存の連携アプリが受け取っている値

BR-048 ホストは、`Document` 全体をそのまま連携アプリへ渡してはならない。連携アプリごとの投影を行い、必要な値のみを渡さなければならない。

BR-049 既存の連携アプリが参照している値は次のとおりである。新しい連携アプリの実装者は、ここに現れないメタが現時点でどの表示にも反映されていないことを前提にしなければならない。

| 連携アプリ | 参照しているメタ | 対象とするノード |
|---|---|---|
| カレンダー | `schedule`・`repeat`・`plan`・`tentative`（`schedule` の仮置き） | `schedule` を持つ `task` のみ |
| ガント | `schedule`・`repeat`・`plan`・`due`（`milestone` として）・`tentative`（`schedule` の仮置き） | `schedule` を持つ `task`、およびその祖先（`list`・セクション） |
| かんばん | `schedule`・`due`・`priority`・`tags` | すべての `task` |
| アジェンダ | `schedule`（終了日）・`due`・`priority` | 未完了（`done`・`cancelled` 以外）の `task` |

BR-050 カレンダーへの投影では、`status` を3値に丸めなければならない（`in_progress` はそのまま、`done` はそのまま、それ以外（`planning`・`ready`・`waiting`・`deferred`・`cancelled`）は `ready`）。連携アプリが7値すべてを必要とする場合、投影を新規に定義しなければならない。

BR-051 ガントへの投影では、自身に `schedule` を持たないグループの期間を、子孫タスクの最小開始・最大終了から算出しなければならない。

BR-052 ガントへの投影は、`schedule` を持たず子孫にも `schedule` を持たないサブタスクを、期間を持たないノードとして出力できなければならない。この出力は既定では行わず、ホスト側の指定があるときのみ行わなければならない。

BR-053 かんばんへの投影では、複数ファイルが渡された場合にのみ、階層の先頭にファイル名（拡張子なし）を追加しなければならない。単一ファイルの場合は追加してはならない。

BR-054 かんばんへの投影では、タスク直下の引用（`quote`）およびメモ（`isMemo` な `list`）の本文を連結して説明文としなければならない。

BR-071 ガントへの投影では、`task` タイプの `GanttNode` に対し次を設定しなければならない。値が無い・パースに失敗した場合は、そのフィールド自体を出力してはならない。

- トップレベル `status`: `node.status`（丸めない、7値そのまま）
- `plan`: `node.meta.plan` をパースした `{ start, end }`（`Luxon DateTime`）
- `milestone`: `node.meta.due` をパースした値。単一点なら `DateTime`、期間（`開始/終了`）なら `{ start, end }`
- `tentative`: `node.meta.tentative?.schedule === true` の場合のみ `true`

`list`（`ListNode`）由来の `subsection` ノードには `plan` のみ設定してよい。`ListNode` は `status` を持たないため、`status` を設定してはならない。

BR-072 カレンダーへの投影では、`Task` に対し次を設定しなければならない。値が無い・パースに失敗した場合は、そのフィールド自体を出力してはならない。

- `plan`: `node.meta.plan` をパースした `TimeSpan`
- `tentative`: `node.meta.tentative?.schedule === true` の場合のみ `true`

> **注釈 A-09（かんばんは `@plan`・仮置きを投影していない）**: `@plan` と `?`（仮置き）は解析処理には実装済みであり `meta` に現れる。カレンダー（BR-072）とガント（BR-071）はこれらを投影に反映しているが、かんばんはいずれも参照していない（`@due` はかんばんとアジェンダのみ参照する）。かんばんカードへの `@plan`・仮置きの反映は未実装である。新しい連携アプリがこれらを扱う場合、投影の新規実装がホスト側に必要である。

> **注釈 A-10（`@repeat` は表示範囲を渡さないと消える）**: `@repeat` を持つタスクは、投影時に表示範囲（開始・終了）を与えた場合にのみオカレンスへ展開される。表示範囲を与えない場合、そのタスクは**一切出力されない**（展開前の `@schedule` も出力されない）。展開されたオカレンスの識別子は `<globalKey>__r<連番>` の形を取り、これは `globalKey` ではないため、そのまま書き戻しに使用できない。連携アプリは、書き戻し時に `__r<連番>` を除去しなければならない。

> **注釈 A-11（日付のみの期間の終端解釈が一致していない）**: `2026-06-01/2026-06-05` のように時刻を含まない期間について、現行のカレンダー投影は終端を排他として扱い、6月5日を含めずに描画する。一方、時間メタ3層モデルの Spec（`time-meta-model.spec.md`）は「日付のみの場合は終日（00:00〜23:59）」と規定しており、これに従えば6月5日を含む。両者は1日ずれる。どちらを正とするかは未決定である。新しい連携アプリは、いずれの解釈を採るかを実装時に明示しなければならない。

### 4.8 書き戻し

BR-055 連携アプリ上の操作（ドラッグによる日時変更等）を Markdown へ反映する場合、`onNodePatch` を呼び出さなければならない。

BR-056 `onNodePatch(globalKey, patcher)` の `patcher` は次のシグネチャでなければならない。`patcher` は副作用を持たない純粋関数でなければならない。

```ts
(md: string, doc: Document, node: TaskNode) => string
// md   : 対象ファイルの現在の全文
// doc  : 対象ファイルの現在の解析結果
// node : globalKey が指すタスクノード
// 戻り値: 書き込むべき新しい全文
```

BR-057 ホストは、`globalKey` から対象ファイルとノードを解決し、ファイル全文を読み、`patcher` を適用し、結果が元と異なる場合にのみ書き込まなければならない。

BR-058 ホストは、`globalKey` が解決できない場合、何も書き込まずに終了しなければならない。例外を投げてはならない。連携アプリは、書き戻しの成功を前提にしてはならない。

BR-059 書き戻しは、`globalKey` が指すファイル1件のみに作用しなければならない。他のファイルを変更してはならない。

BR-060 メタを書き込む場合、対象タスクの子の領域に既存の同種メタがあれば最初の1個を置換し、無ければ子領域の末尾に挿入しなければならない。挿入時のインデントは「対象タスクのインデント + 2スペース」でなければならない。

BR-061 既存のメタ行に `?`（仮置き）が付いている場合、書き換え後も `?` を保持しなければならない。

BR-062 連携アプリは、書き戻し後に自身の内部状態を更新してはならない。ホストが再解析し、`registerUpdater` で登録された関数を通じて新しいソースを渡す。

### 4.9 エディタからのドラッグ＆ドロップ

BR-063 ユーザーがエディタ上のタスク行をドラッグした場合、ホストは MIME タイプ `application/x-md-task` でペイロードを `DataTransfer` に設定しなければならない。

BR-064 ペイロードは次の構造の JSON 文字列でなければならない。

```ts
interface TaskDragPayload {
  sourcePath: string   // vault ルート相対パス
  line: number         // 0 始まりの行番号
  nodeId: string       // localId（globalKey ではない）
}
```

BR-065 連携アプリは、受け取った `sourcePath` と `nodeId` を `<sourcePath>::<nodeId>` の形に連結して `globalKey` を復元し、`onNodePatch` へ渡さなければならない。

### 4.10 クリック連動と再読込

BR-066 連携アプリは、アイテムがクリックされた場合、`onNodeClick(globalKey)` を呼び出さなければならない。ホストは該当ファイルを開き、該当行へカーソルを移動する。

BR-067 連携アプリは、再読込を要求する場合、`onReload()` を呼び出さなければならない。ホストは全対象ファイルを再解析する。

BR-068 連携アプリは、`onNodeClick` および `onReload` の呼び出し結果を待って動作を変えてはならない。いずれも戻り値を持たない。

## 5. 非振る舞い制約（NON-BEHAVIORAL CONSTRAINTS）

- Markdown が唯一の正の情報源である。連携アプリが保持する状態は、再解析によって上書きされ得る派生物として扱わなければならない。
- 連携アプリは、ホストから独立した汎用ライブラリとして開発する。特定の業務語彙を型名・prop 名に持ち込まない。
- 投影は純粋関数として実装し、同一入力に対して同一出力を返す。
- 連携アプリは、本 Spec に記述のない振る舞いに依存してはならない。

該当なし（本 Spec は状態遷移を持つエンティティを定義しない）。

## 7. 境界条件（EDGE CONDITIONS）

- ファイルが空である場合、`sections` は空配列となる。
- 値が空のメタ行（`@plan:`）は、キーが除去されずに空の値として `meta` に現れる（注釈 A-12）。
- `?` の位置が不正な場合（`@schedule ?:`・`@?schedule:`）、そのメタ行は受理されず、`meta` に反映されない。
- 終了が開始より前である期間（`2026-06-05/2026-06-01`）は、`meta` にはそのまま現れる。既存の投影はこれを検出して当該アイテムを除外している。連携アプリも同様に検出しなければならない。
- `repeat` の規則が不正な場合、オカレンスは0件となり、当該タスクは表示されない。
- ファイル全体が共通のインデントを持つ場合、ホストは最小インデントを除去してから解析する。`lineNumber` は元ファイルの行番号のままである。
- メタ行が誤ったインデントで子リストを巻き込んだ場合、その子ブロックは親タスクの `children` へ再配置される。
- `onNodePatch` に渡した `globalKey` が解決できない場合、書き戻しは黙って無視される。
- 繰り返し展開後の識別子（`<globalKey>__r<連番>`）をそのまま `onNodePatch` へ渡した場合、書き戻しは無視される。
- 同一タスクが複数の連携アプリに同時に表示されている場合、いずれかが書き戻すと、全アプリへ再解析後のソースが配信される。

---

## 8. 対象外（OUT OF SCOPE）

- プロセス外通信（HTTP・IPC・ファイル出力）およびそのシリアライズ形式（注釈 A-01）。
- 認証・暗号化・アクセス制御。
- 差分更新・増分同期・変更通知の購読機構。連携アプリは常に全ソースを受け取る。
- 編集に耐える恒久識別子（注釈 A-08）。
- `@plan` 継承の実装（注釈 A-07）。
- かんばんへの `@plan`・仮置きの投影および描画（注釈 A-09）。カレンダー・ガントへの投影は BR-071・BR-072 で規定済み。
- 日付のみの期間の終端解釈の統一（注釈 A-11）。
- 表示仕様（色・線幅・レイアウト・操作感）。
- 連携アプリ内部の状態管理・永続化。

### 9.1 実例（参考。振る舞いを定義しない）

以下はすべて、実際に解析・投影を実行して得た出力である。本書と同じ場所に、同じ方法で生成した実例ファイルを置いている。

| ファイル | 入力 Markdown | 規模 | 用途 |
|---|---|---|---|
| `sample-external-data-s.json` | `demo/sample-s.md`（96行） | タスク13件・カレンダー10件・ガント15件 | 最初に読む最小例。見出し・グループ・タスク3種（`ready`/`in_progress`/`done`）・`@schedule`・`@due`・`@priority`・`@tags`・引用のみ |
| `sample-external-data-m.json` | `demo/sample-m.md`（266行） | タスク44件・カレンダー52件・ガント71件 | 実務相当。ステータス7種すべて・`@plan`・仮置き `?`・`@repeat`・`@dependsOn`・各種の期間表記・4階層の入れ子 |
| `sample-external-data-l.json` | `demo/sample-l.md`（753行） | タスク126件・カレンダー98件・ガント147件 | 網羅版。多段 WBS と部門横断の業務パターンに加え、本書の注釈 A-05・A-06・A-10・A-12 に該当する入力の実際の出力を含む |

いずれのファイルも、`sources`（連携アプリへ渡される `SourceEntry[]`）と `projections`（各連携アプリが受け取る投影結果）を含み、先頭の `_about` に生成条件（表示範囲・基準日）を記載している。

入力 Markdown（`総務/2026-06.md`）:

```markdown
# 総務 2026年6月
```

この実例から読み取れる事実:

- `@plan` は `meta.plan` に解析され、カレンダー（`plan`。BR-072）とガント（`plan`。BR-071）の投影に渡る。かんばんへは渡っていない（注釈 A-09）。
- `@schedule?` の仮置き情報は `meta.tentative.schedule` に入り、カレンダー・ガントの投影結果では `tentative: true` として現れる（BR-071・BR-072）。かんばんへは渡っていない（注釈 A-09）。
- `@due` は、ガントの投影結果では `milestone` として現れる（単一点のため `DateTime` の ISO 文字列。期間指定の場合は `{ start, end }` になる。BR-071）。
- タスクの `path` は自身を含み添字が付くが、カレンダーの `parents` では両方とも除去されている（注釈 A-03）。
- ガントは、`@schedule` を持つタスクの祖先セクション・祖先グループを、子孫の期間を集約したノードとして出力する（BR-051）。
- かんばんは単一ファイルのため、階層にファイル名を含めていない（BR-053）。

### 9.2 新しい連携アプリを追加する場合の実装単位

新しい連携アプリを追加する場合、ホスト側には次の4点が必要である。既存のカレンダー連携が参照実装である。

1. **投影**: ソース配列を受け取り、連携アプリ固有の型の配列を返す純粋関数。
2. **タブ**: 投影を呼び出し、連携アプリのコンポーネントへ props を渡し、操作イベントを `onNodePatch` へ橋渡しするコンポーネント。
3. **マウント**: `ViewMountProps` を受け取り、フィルタを適用してタブへ渡すコンポーネント。
4. **ビュー**: Shadow DOM を用意し、マウントコンポーネントを配置するホスト側のビュークラス。

連携アプリ側には、汎用的な prop を受け取るコンポーネントと、操作結果を通知するコールバックのみを実装する（BR-043〜BR-047）。

## 10. 変更管理（CHANGE CONTROL）

本 Spec は現行実装の記述である。実装が変わった場合は、本 Spec を同時に更新しなければならない。実装を変えずに本 Spec のみを変更してはならない。

注釈（A-01〜A-12）は、対応する論点が決着した時点で、該当する BR 本文へ昇格させ、注釈自体を削除しなければならない。

BR 番号は公開後に変更してはならない。要件を廃止する場合は、番号を再利用せず deprecated として明記しなければならない。

本 Spec に記述のない振る舞いは存在しない。記述の欠如は禁止を意味する。連携アプリは、記述のない振る舞いを前提にしてはならない。
